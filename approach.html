Typing tutor: building choices

This note covers the client stack, the server, and how the program takes over the keyboard. It is a design note, not the final spec. Nothing has been built yet.

What the TypeAbility manual gives us

  • A spoken-first program. The student never needs to look at the screen.
  • Function keys as the control panel: F1 repeat, F2 next or repeat, F3 pick a lesson, F4 dictation, F5 race, F11 teacher mode, F12 progress.
  • Ninety-nine lessons that move from finding the function keys, through the home row, the top and bottom rows, capitals, numbers, punctuation, navigation, editing, selecting, copy and paste, and the numpad.
  • Instant feedback after every key. A wrong key gets the right key spoken. A repeated mistake gets the key's location described.
  • Each task is typed two or four times. Each lesson ends with accuracy and speed.
  • Dictation in chunks of three or four words, word-level echo at a higher pitch, then accuracy, speed, and spelling tips.
  • Races: a timed speed and accuracy run on the current task.
  • Per-student records, a session report, a full history, and a shared folder so a student can move between computers.
  • Preferences for typing experience, speech rate, double-press speed, one-handed typing, laptop keyboard, and dictation echo.

What TypingClub's staff side gives us

  • Classes, and students enrolled in a class.
  • A scoreboard: stars, practice time, average accuracy, average speed, overall progress.
  • A per-student view for each lesson.
  • An attempt history, in order, with a way to open one attempt.
  • A students-by-lessons grid, so a teacher sees who is stuck.
  • Daily and weekly practice time, and CSV export for grading.
  • A lesson plan the teacher can reorder or trim, with per-class goals.

Three ways to build the client

Option A: Python with wxPython, and Prism through the Python binding

What it is
One Python program. wxPython draws the windows and dialogs. Prism talks to the screen reader. The lesson area is a custom drawing surface that the screen reader cannot see into, so Prism is the only voice during a lesson.
Good
It uses each platform's own controls. On Windows that means real Win32 controls, the same kind NVDA is built from, so NVDA and JAWS read them the way they read any native program. On Linux, wxGTK passes the work to GTK, which is what Orca reads. On macOS it uses Cocoa controls. NVDA itself is written in wxPython, so Windows behavior is proven. Prism's Python binding works here today. Full keyboard capture is practical on each platform.
Bad
Installers are large, around 60 to 90 megabytes. There are no Linux wheels on PyPI, so Linux uses the distribution package or a bundled build. Some wx controls are drawn by wx itself rather than the platform, so the design will use native lists, choices, and text fields instead of the generic ones.
Verdict
The recommended option.

Option B: Python with Qt, the earlier recommendation

What it is
PySide6 and Qt 6, with Qt's own accessibility bridge to each platform.
Good
Modern widgets, strong layout and drawing, and good documentation.
Bad
Qt draws its own controls and then describes them to the screen reader, and that description is unreliable. In Qt 6.11.1 with PySide6, a list box does not take keyboard focus or announce its selection in VoiceOver, a combo box changes value without speaking, and a tree view can crash the program while VoiceOver is running. Older NVDA reports show the same pattern with tree views and editable combo boxes. These are exactly the controls a lesson picker and a preferences dialog need.
Verdict
Rejected. The risk lands on the screens blind students use most.

Option C: Rust with a native window toolkit, and Prism's Rust binding

What it is
A small compiled program, custom-drawn, with Prism called directly.
Good
Small download, exact control of every key, strong performance, one binary per platform.
Bad
Custom-drawn interfaces have young accessibility support, especially on macOS. Hitting WCAG 2.1 AA means building the accessibility tree by hand. Much slower to build, and harder for you to change later.
Verdict
Only worth it if installer size or performance becomes a real problem.

Rejected outright: a web interface inside a desktop shell

Tauri or Electron would look good and share code with the dashboard, but the web view takes some keys before the page sees them. Control W, F5, F11, Alt Left, and Tab are handled by the browser itself, which directly conflicts with teaching every key. The page is also exposed to the screen reader, so lesson text is spoken twice unless it is hidden, and hiding it is fragile.

Recommendation

Client: Python 3.13 with wxPython 4.3.2 and the Prism Python binding. Windows first. macOS and Linux use the same code with their own key capture layer.

Server: FastAPI with PostgreSQL, behind a Caddy reverse proxy that obtains and renews the HTTPS certificate. The dashboard is ordinary server-rendered HTML with small amounts of JavaScript, so it works with any screen reader and is easy to audit against WCAG 2.1 AA. Staff open it in a browser on the school domain. Students' clients sync to it over the internet and keep working offline.

Why: wxPython gives each platform's real controls, which is the one thing that reliably makes menus, lists, and dialogs speak. Prism owns every word during a lesson. The server is small enough for one Linux machine and safe to expose on a domain.

Taking the whole keyboard

During a lesson the client grabs the keyboard, so Tab, Enter, Control, Alt, the function keys, and left versus right Shift all reach the lesson. Capture sits in a small platform layer. The lesson logic itself never touches the operating system, so it can be tested without a real keyboard.

Windows
A low-level keyboard hook in a background thread. It needs no administrator rights. It sees left and right Shift, Control, and Alt separately, and it can swallow Alt Tab and the Windows key. Control Alt Delete and Windows L are never blocked.
macOS
A system event tap, which needs a one-time Accessibility permission. The setup screen detects whether permission is granted and explains how to grant it. Command Tab and Command Q can be swallowed. The screen lock shortcut cannot.
Linux
A keyboard grab on the window under X11. Under Wayland a program cannot grab the whole keyboard, so capture happens inside the window only and some desktop shortcuts will still fire. The app will say so.
Always available
Escape pressed three times ends a lesson and releases the keyboard within about a second, as in TypeAbility. A separate chord, Control Alt Shift X, also releases it and is never taught. Both are announced when a lesson starts.

Risks and how we check them

  • macOS control coverage. wx uses Cocoa controls, but a few wx controls are drawn by wx itself. The design sticks to native ones, and we test on your Mac over SSH before promising macOS support.
  • Linux packaging. wxPython has no Linux wheels on PyPI. Linux installs from the distribution package, or ships a bundled build. Linux is last, so this does not block the first release.
  • Key capture versus antivirus. A low-level hook can look suspicious to some security software. We sign the installer and keep the hook active only during a lesson.
  • Keyboard layout. The course teaches key positions, so it assumes a US QWERTY layout. The client detects and warns about other layouts instead of teaching the wrong finger.
  • Content. We write our own lesson text and word lists from the manual's progression. We do not copy TypeAbility's wording or its jokes.
  • Public server. A domain on the internet means HTTPS only, hardened sign-in, rate limiting, and nightly database backups kept off the machine.
