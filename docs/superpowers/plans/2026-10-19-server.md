# SteadyType Server and Dashboard Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A self-hosted FastAPI server with a staff dashboard, student sign-in, and attempt sync, deployable on Ubuntu behind Caddy.

**Architecture:** SQLAlchemy models over SQLite in tests and PostgreSQL in production. Staff use a password and a signed session cookie. Students use a username and receive a long-lived device token for the client. The dashboard is server-rendered Jinja2 with native HTML controls, no JavaScript framework.

**Tech Stack:** Python 3.13, FastAPI, SQLAlchemy 2, Jinja2, itsdangerous, passlib-free scrypt, pytest, httpx.

**Spec:** `docs/superpowers/specs/2026-10-19-steadytype-design.md`

**This is plan 3 of 3.**

## Global Constraints

- HTTPS only in production. Caddy terminates TLS; the app trusts forwarded headers.
- Every dashboard page meets the accessibility rules A-1 to A-12 in the spec.
- Staff may read only their own classes. Admin may read all.
- Attempts are idempotent by client UUID.
- Student usernames are lastname.firstname and are the whole student credential.
- No student email address exists anywhere.
- CSRF token on every state-changing form.

## Review Focus

1. A teacher opens another teacher's class URL. The page must answer 404 or 403, never data.
2. The same attempt uploads twice. The second upload must not duplicate it or change the first.
3. A student token is used after it expires or after the account is disabled. The API must refuse.
4. A dashboard table with 40 students must still be readable by a screen reader at 200 percent zoom.
5. The server starts with no staff account. Setup must create one and never log the password.
